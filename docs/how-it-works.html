Three simple layers, each with one job

Where the data is saved

One app, two stock rooms — chosen automatically

The portal can keep its information in two different places, and it decides which one to use the moment it starts. Nobody chooses in the code — you simply tell it whether a database is available.

❓
On start-up it asks:
“Do I have a database?”
DATABASE_URL
⟶
No — save to a file on this computer Laptop

Everything goes into one tidy file, data/ctp-data.json, with photos and certificate sheets beside it in uploads/. Ideal for testing at home. Back it up by copying two folders.

⟶
Yes — save into the database Live site

The very same information goes into Postgres instead. This is what the public site uses, because the free host erases its own hard disk every time the app restarts. The database remembers; the disk does not.

What is kept, and in which drawer

DrawerWhat goes in itName online
The record book Centres, addresses, zones, coordination teams, volunteers, sessions, certificate reflections, enrollments, news and logins ctp_state
The filing cabinet Uploaded files — centre photographs and certificate spreadsheets, stored as the actual bytes ctp_blobs
The safety net Automatic snapshots taken before anything destructive happens, so a mistake can always be undone ctp_backups

How your data is protected

🔒

Passwords are never stored

Only a scrambled fingerprint is kept. Even someone holding the whole database cannot read anyone's password — not even yours.

👁

Private stays private

Phone numbers, emails and volunteer rosters are removed before anything is sent to the public — not merely hidden on screen.

🔄

Nothing half-written

Saves are all-or-nothing and happen one at a time, so a power cut can never leave the records in a broken state.

💾
Taking a backup takes one click

Admin console → Backup downloads the entire portal as a single file you can keep on a pen drive or in email. Password fingerprints are deliberately left out of that file, so it is safe to store and share internally.

What actually happened, step by step

  1. The code was published to GitHub as a public repository under the MIT licence, so the work is permanently preserved and anyone may reuse it.
  2. A free Neon database was created in Singapore — the nearest region to India — and its connection details were handed to the host as a secret.
  3. Render was pointed at the repository. A small instructions file in the project, render.yaml, already told it everything (shown below).
  4. The administrator account was created on first boot from settings held in Render's dashboard, never written into the code.
  5. It went live — and now every change pushed to GitHub rebuilds and republishes the site automatically, with no manual uploading ever again.
⚡

Updating takes one command

A change is saved to GitHub, Render notices within seconds, rebuilds and swaps the new version in — two to three minutes, no downtime. Exactly how the centre-photo feature reached the live site.

✅

Nothing ships untested

Before any release, 153 automated checks run through the portal — logins, centres, photo uploads, and confirming people cannot see data that is not theirs. Run against both storage modes. All 153 passed.

The entire hosting instruction, in eight settings

# render.yaml — Render reads this and needs nothing else
type: web      runtime: node      plan: free
region: singapore ← nearest to India
buildCommand: npm ci ← fetch the five outside parts
startCommand: npm start ← switch the portal on
healthCheckPath: /api/health ← keep checking it is alive
envVars: DATABASE_URL, CTP_ADMIN_EMAIL, CTP_ADMIN_PASSWORD
         ↑ only the names of the secrets live here. The values are typed into
           Render's dashboard — which is why the project can safely be public.

The one honest trade-off

😴
The site naps when nobody is using it

After 15 minutes with no visitors, the free plan puts the app to sleep. The next person to arrive waits roughly 30–60 seconds while it wakes up; everyone after them gets an instant site. Nothing is lost during a nap — the data sits in the database, not on the sleeping machine.

⏰

Fix it for free

A free UptimeRobot monitor visiting the site every 5 minutes keeps it awake through the working day. Still ₹0.

💰

Or pay to remove it

About $7 a month on Render's Starter plan removes the sleep entirely and allows a custom web address.

🔗

Nothing is locked in

The same code runs on Azure, on a college server, or on a laptop. Changing host needs no code changes at all.

💡
Why a charity directory fits inside “free” so comfortably

Free tiers are sized for hobby projects, and this portal is genuinely small. Even the whole national directory with photographs occupies a small fraction of the 0.5 GB the database gives away.

“What if one of these free services stops?”

If this changed…What it would take to recover
Render stops being free Move to another host. The project already carries instructions for Azure, and the same code runs unchanged on any computer with Node installed.
Neon stops being free Point DATABASE_URL at any other Postgres database and restart. Postgres is a 30-year-old open standard, not a proprietary product.
GitHub changes A full copy of the code and its entire history already sits on the laptop it was written on, and on every machine that has ever downloaded it.
Everything goes at once The one-click backup file plus the public code rebuilds the portal from scratch on a laptop in minutes.
